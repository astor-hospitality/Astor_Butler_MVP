# Счета гостя и журнал операций

Дата: 2026-10-07. Автор: Дима (`@dmtrshm`). Для Михаила на ревью, для Codex и для того, кто продолжит оплату через Saby Presto.

Карта API Saby и блокеры — в [SABY_PRESTO_BOOKING_API.md](SABY_PRESTO_BOOKING_API.md), план интеграции — в [SABY_INTEGRATION_PLAN.md](SABY_INTEGRATION_PLAN.md).

## 1. Итог

Butler получил собственный учёт счетов: счёт на каждый заказ, предварительную сумму по своему меню, журнал всех операций и журнал вызовов Saby. Денег Butler не принимает и ссылку на оплату пока не выдаёт.

Всё выключено по умолчанию. С выключенными флагами ничего не пишется и ни один HTTP-вызов не наблюдается.

Это первая из четырёх частей:

| Часть | Что | Состояние |
| --- | --- | --- |
| 1 | Счёт, предварительная сумма, журнал операций, журнал вызовов Saby | Этот PR |
| 2 | Ссылка на оплату из Saby (`payment-link`), «мои счета» в боте | Не начата, нужны ключи и эквайринг в Presto |
| 3 | Счёт за столом в зале | Не начата, у Presto нет публичного метода, см. раздел 9 |
| 4 | Отчёты по активности гостей и сбоям | Не начата, данные для неё уже копятся |

## 2. Правила

1. **Butler не принимает оплату.** Платёж проходит в Saby. Butler только хранит копию того, что сообщил Saby.
2. **«Оплачен» ставит только ресторан.** Счёт становится `PAID`, когда Saby вернул `payState` 10 или 200. Незнакомый код — это `UNKNOWN`, а не «оплачен».
3. **К оплате идёт сумма Saby.** Расчёт Butler — предварительный, для показа гостю до отправки заказа.
4. **Журнал только пополняется.** У `BillOperationRepository` нет методов изменения и удаления.
5. **В таблицах счетов нет имён и телефонов.** Счёт ссылается на чат и на бронь, где эти данные уже лежат.

## 4. Данные

| Таблица | Что хранит |
| --- | --- |
| `guest_bills` | Счёт: чат, заведение, вид, бронь, заказ в Saby, статус, статус оплаты, расчёт Butler, сумма Saby |
| `guest_bill_lines` | Позиции, по которым считали: блюдо, количество, цена на момент расчёта |
| `bill_operations` | Журнал: тип операции, успех, кто инициировал, код ошибки, пояснение, время |
| `saby_call_log` | Вызовы Saby: метод, путь, код ответа, исход, длительность, время |

Суммы хранятся в копейках целым числом. На одну бронь — один счёт одного вида; на один заказ Saby — один счёт.

## 5. Статусы

Статус счёта:

| Статус | Значение |
| --- | --- |
| `ESTIMATED` | Butler посчитал сумму, заказа в системе ресторана нет |
| `ISSUED` | Заказ есть в системе ресторана |
| `PAID` | Ресторан сообщил, что платить больше нечего |
| `CANCELLED` | Счёт отменён. Оплаченный счёт отменить нельзя: возврат делает ресторан |

Статус оплаты по `payState` из ответа `GET /retail/order/{id}/state`:

| `payState` | В Saby | В Butler | Счёт оплачен |
| --- | --- | --- | --- |
| 0 | не оплачено | `UNPAID` | нет |
| 10 | предоплата 100 % | `PREPAID_FULL` | да |
| 30 | предоплата | `PREPAID_PARTIAL` | нет |
| 50 | отгрузка в кредит | `CREDIT` | нет |
| 200 | полный расчёт | `PAID` | да |
| другое или нет поля | — | `UNKNOWN` | нет |

Счёт следует за рестораном в обе стороны: если после «оплачено» Saby сообщает «не оплачено», счёт возвращается в `ISSUED`, а переход остаётся в журнале.

Операции в журнале: `ESTIMATE_CREATED`, `ISSUED_TO_VENUE`, `VENUE_SUBMIT_FAILED`, `PAY_STATE_CHANGED`, `VENUE_AMOUNT_REPORTED`, `AMOUNT_MISMATCH`, `CANCELLED`.

## 6. Предварительная стоимость

Сумма считается из каталога Butler, без Saby, поэтому доступна и при недоступном Saby.

- **Ланч без сетов:** цена блюда × количество, сумма по всем блюдам.
- **Ланч с сетом:** цена сета × число гостей. Блюда сета записаны в счёт как входящие в цену и к сумме ничего не добавляют.
- **Нет цены хотя бы у одной позиции:** суммы нет вовсе, счёт открывается без неё. Частичную сумму Butler не показывает.

Почему сумма только предварительная:

- в ней нет скидок, бонусов и сервисного сбора — их считает ресторан;
- цены взяты из `business-lunch/aeris.json`, где стоит `confirmedByVenue: false`;
- цена в прайс-листе Presto может отличаться.

Когда Saby сообщит свою сумму, она записывается рядом с расчётом. Расхождение попадает в журнал как `AMOUNT_MISMATCH` — это сигнал обновить каталог.

Сейчас счёт открывается только для бизнес-ланча: это единственный заказ блюд, который Butler оформляет. Цены основного меню лежат в `menu/aeris/site/kitchen.json`, но заказа по нему в Butler нет.

## 7. Журнал вызовов Saby

Перехватчик добавляется ко всем `RestTemplate` приложения, потому что каждый клиент Saby собирает свой. Вызовы на другие адреса он пропускает без записи.

Что записывается: метод, путь, код ответа, исход (`OK`, `HTTP_ERROR`, `IO_ERROR`), длительность.

Что не записывается: тела запросов и ответов, заголовки, токен, параметры запроса. Идентификаторы в пути заменяются на `{id}`, поэтому `/retail/order/<UUID>/state` хранится как `/retail/order/{id}/state`.

Перехватчик только наблюдает: исход вызова он не меняет, а ошибка записи в журнал вызов не ломает.

`SabyCallLogRepository.summarySince(момент)` возвращает по каждой операции число вызовов, число сбоев, среднюю и наибольшую длительность; сначала идут операции с наибольшим числом сбоев.

## 8. Настройки

```text
ASTOR_BILLING_ENABLED          вести счёт и журнал для заказов Butler, по умолчанию false
ASTOR_SABY_CALL_LOG_ENABLED    записывать вызовы Saby, по умолчанию false
```

В `docker-compose.prod.yml` эти переменные не проброшены: файл в этом PR не менялся. Чтобы включить флаги на стенде, проброс нужно добавить отдельно.

## 9. Чего нет и что дальше

**Подключение к стеку Saby.** Этот PR сделан от `main` и не зависит от открытых PR #38, #41, #47–#52. Поэтому две связи остаются на потом:

| Связь | Когда | Что сделать |
| --- | --- | --- |
| Счёт становится `ISSUED` | После PR #51 (блюда ланча уходят в Saby) | Ничего: `LunchBillRecorder` уже читает ответ провайдера. До #51 провайдер заказ не принимает, и счёт остаётся `ESTIMATED` |
| Счёт получает статус оплаты | После PR #48 (`ExternalBookingSync`) | В опросе статусов прочитать `payState` через `SabyPayState.read` и вызвать `GuestBillService.venueReported` |

Вторая связь не добавляет вызовов Saby: `payState` приходит в том же ответе `order/states`, который опрос уже читает.

**Ссылка на оплату.** `GET /retail/order/{id}/payment-link` не вызывается. Форма ответа неизвестна до первого живого вызова, а в Presto должен быть настроен эквайринг.

**«Мои счета» в боте.** `GuestBillService.billsOf` есть, сценария в FSM нет. Новый сценарий меняет FSM и идёт вместе с оплатой.

**Счёт за столом.** В публичном API Presto есть доставка, бронь, бонусы, стоп-лист и вебхуки; метода «открытый чек стола» или «пречек» нет. Нужно спросить поддержку Saby или проверить на ключах, продолжается ли заказ брони как счёт стола под тем же идентификатором.

**События в Kafka.** Операции по счетам в outbox не пишутся. Всё, что попадает в топик `astor.user.events`, пересылается в админский чат Telegram; для счетов нужен отдельный топик и решение по контракту в `docs/contracts/KAFKA_TOPICS.md`.

**Очистка `saby_call_log`.** Строки не удаляются. При опросе раз в минуту это около полутора тысяч строк в сутки.
