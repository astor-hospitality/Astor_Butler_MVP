## 2. Как сейчас устроено

### 2.1. Кто такой гость

| Канал | По чему узнаёт Butler | Где хранится | Попадает в `users` |
| --- | --- | --- | --- |
| Telegram | `telegram_user_id` | `users` (по `telegram_id`), `telegram_profiles`, телефон в `user_contacts` | да (`IdentityService.identifyTelegram`) |
| MAX | id чата MAX → внутренний `chat_id` из диапазона `8e12+` | `messenger_chat_bindings` (имя, username, `contact_phone`) | нет |
| Веб-чат | сессия браузера → `chat_id` из диапазона `9e12+` | `web_sessions`; телефон только в самой заявке (`guest_phone`) | нет |

Один человек в трёх каналах — три разных гостя. По телефону никто не склеивает. В `users` поле `telegram_id` обязательное и уникальное (миграция `2025-06-19-create-users.yaml`, сущность `User`), поэтому гость MAX или веба туда не помещается без миграции.

## 5. Предлагаемая модель

```
                      гость в Butler (users.id)
                                │
     ┌──────────────┬───────────┼──────────────┬────────────────────────┐
  Telegram id    MAX id     веб-сессия    телефон (E.164)        клиент Saby (UUID)
  при первом     при первом  на время      подтверждён, если       по подтверждённому телефону,
  сообщении      сообщении   сессии        гость прислал свой      когда Saby ответит на вопросы 1–3
                                           контакт
                                                                         │
                                                                 карта, бонусы, покупки —
                                                                 остаются в Saby
```

- Гость — это `users.id`. Новых таблиц `guests` / `guest_identities` не нужно; нужно снять обязательность `users.telegram_id` и добавить `user_id` в `messenger_chat_bindings`, `web_sessions`, `visit_reviews`.
- Гость веба заводится в `users` не на каждую сессию, а когда в вебе появились телефон или заявка: анонимные сессии удаляются через 30 дней, записи в `users` остались бы сиротами.
- Склейка каналов — только по подтверждённому телефону. По имени не склеиваем. Номер, вписанный в веб-форму, даёт предположительную связь, которую подтверждает менеджер.
- Факты (заявки, предпочтения, счета, оценки) дозаполняются `user_id` по `chat_id`: диапазоны `chat_id` у каналов не пересекаются. Веб-заявки старше 30 дней — только по `guest_phone`, связь предположительная.
- Карту лояльности Butler не хранит: связь через UUID клиента Saby, данные спрашиваются у Saby.
- Предпочтения — только из явных данных (пожелания к заявкам, заметки персонала). Из переписки не извлекаем.
- Сводка для хостес в карточке заявки вместо переписки: «N заявок, последняя дата, рассадка, последняя оценка». Без трат и без аллергий до ответа юриста (см. 7).
- Ограничение модели: карточка описывает того, кто бронирует, а не того, кто ест.

### Слияние и уникальность

Запись в `users` создаётся при первом сообщении в каждом канале, поэтому к моменту, когда гость подтвердит номер в Telegram и в MAX, у него уже две записи. «Склеить» значит объединить их.

Правило «один подтверждённый номер — один гость»: уникальный индекс по нормализованному номеру среди подтверждённых (`verified_at IS NOT NULL`). Двух записей с одним подтверждённым номером быть не может, поэтому решение принимается **в момент второго подтверждения** — когда номер, уже подтверждённый у записи A, подтверждает запись B:

| Условие при втором подтверждении | Что происходит |
| --- | --- |
| Гость B прошёл код в канал записи A (см. «Подтверждение кодом») | A и B сливаются, факты переносятся |
| Кода нет, но подтверждение у A не старше N месяцев (R9) | A и B сливаются |
| Иначе | Номер переходит к B без слияния: у A подтверждение снимается. Номера у операторов переходят к новым людям |
| Предположительная связь (номер из веб-формы, номер из старой заявки) | Не сливается автоматически; шаг 11, менеджер после появления входа персонала |

### Подтверждение кодом

Предложено 2026-10-11. Гость доказывает, что владеет двумя каналами, кодом или одноразовой ссылкой, и тогда каналы связываются без менеджера. Код решает **связку каналов**, а не подтверждение телефона: свой контакт в Telegram или MAX уже подтверждён мессенджером, там достаточно проверки владельца (шаг 1).

| Ситуация | Нужен код | Почему |
| --- | --- | --- |
| Свой контакт в Telegram или MAX | нет | Мессенджер подтвердил номер; достаточно шага 1 |
| Веб-чат: гость вписал телефон | да | Номер ничем не подтверждён; для веба — код из бота, а не ссылка (см. ниже) |
| Связать Telegram и MAX одного человека | да | Особенно при разных номерах или без контакта |
| Номер мог перейти к другому человеку | да | Код в старый канал отвечает, тот же ли это человек |
| Повторное подтверждение старой базы (F14) | можно | Проще повторно попросить контакт кнопкой (шаг 2а) |

**Главное правило: код отправляется в уже подтверждённый канал гостя, а вводится в новом.** Так гость доказывает владение обоими. Код в канал, который гость только назвал, ничего не доказывает.

Куда слать, по возрастанию цены:

1. **Сообщение бота в Telegram или MAX.** Бесплатно. Бот может написать только тому, кто уже нажимал «Старт»; для связки Telegram ↔ MAX это выполнено.
2. **Для веба — код из бота, вводится на сайте.** Сайт показывает «Подтвердить в Telegram» со ссылкой `t.me/<бот>?start=link`; гость нажимает «Старт», бот присылает **ему** код, гость вводит код на сайте. Код рождается в подтверждённом канале (Telegram) и доказывает владение им в новом (веб). То же для MAX через `bot_started`.
   - **Нельзя** привязывать по одной ссылке с токеном (`start=link_<токен>` → «Старт» → готово): злоумышленник открывает веб-чат, получает ссылку и пересылает её жертве; жертва нажимает «Старт», и сессия злоумышленника привязывается к её аккаунту и истории. Токен в ссылке создан в неподтверждённом канале и ничего не доказывает. Вариант «бот спрашивает: связать с сайтом, открытым только что?» слабее кода и не используется.
3. **Telegram Gateway.** Платный сервис Telegram: код по номеру телефона в Telegram, даже если гость не писал боту. Цену и доступность для российского юрлица уточнить.
4. **SMS или звонок-сброс.** Договор с провайдером, оплата за сообщение, для SMS — регистрация имени отправителя. Только если варианты 1–3 не закроют задачу.

Требования к реализации:

- код 6 цифр, живёт 5–10 минут, одноразовый, в базе только хэш; ссылка — случайный токен с тем же сроком;
- не больше 3–5 попыток ввода, затем новый код;
- ограничение частоты отправки **на получателя**, а не только на отправителя: иначе через бота можно засыпать чужого человека кодами;
- одинаковый ответ, существует номер или аккаунт или нет;
- текст: «Код для связки аккаунтов Astor. Никому не сообщайте его, в том числе сотрудникам ресторана. Если это были не вы — проигнорируйте»;
- каждая попытка — в журнал; при успешной связке записи гостя сливаются по правилам выше.

Что это меняет: склейка, подтверждённая кодом, автоматическая (шаг 7б); шаг 11 остаётся только для спорных случаев; веб перестаёт быть «предположительной связью».

## 6. Консьерж

Предложение: Консьерж не читает карточку гостя из Butler.

- Butler работает от имени ресторана (бот на юрлицо ресторана), Консьерж — от имени Astor (юрлицо Михаила). История визитов, траты и заметки персонала — данные ресторана; передача другому оператору требует отдельного согласия гостя и договора.
- Сводная история «где был, что выбирал, как оценил» по всем ресторанам естественно складывается у самого Консьержа: гость говорит с ним, он отправляет заявки.
- Из Butler в Консьерж — минимум и только по заявкам Консьержа: статус, состоялся ли визит, оценка. Траты, телефон, заметки персонала, визиты мимо Консьержа — нет.
- Сейчас в `data/venues.json` Консьержа один ресторан (AERIS), сводка по ресторанам преждевременна. Решить нужно принцип.

### Вопросы к юристу

- Аллергии — сведения о здоровье, особая категория персональных данных. Можно ли показывать их хостес в групповом чате, и что должно быть в согласии.
- Сроки хранения переписки (предложение 30 дней), карточки (R2) и сроки ответа на запрос об удалении по 152-ФЗ.
- Передача данных в контекст внешней модели (GigaChat), если бот будет знать имя, число визитов и предпочтения.
- Передача данных между рестораном (Butler) и Astor (Консьерж).
- Согласия прошлых лет: часть могла быть дана чужим контактом (F15), отличить их нельзя (F3). Что делать с такими согласиями — запросить заново у всех или нет.
