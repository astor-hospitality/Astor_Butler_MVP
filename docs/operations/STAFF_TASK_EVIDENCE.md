# Кабинет персонала: фото-подтверждения поручений

Дата: 2026-10-11. Автор: Рома (`0xLaki`). Задача: [issue #94](https://github.com/astor-hospitality/Astor_Butler_MVP/issues/94).
Статус: контракт и код есть, по умолчанию выключено. Нигде не включено и не выложено. Типы, размер и срок хранения ниже - предположения, их подтверждает Михаил.

Связанные документы: `STAFF_PORTAL_RUNBOOK.md` (кабинет, вход, включение), `GLASSES_STAFF_TASKS_P1_DRAFT.md` (черновик P1 для очков), `GLASSES_S3_STORAGE.md` и `GLASSES_STEP_PHOTOS.md` (приватный bucket пилота очков, к поручениям не подключён).

## Зачем

У этапа поручения есть признак `evidenceRequired`. Такой этап закрывается только при хотя бы одном фото. До этой работы `POST /api/staff/tasks/{task}/evidence` всегда отвечал `503 EVIDENCE_UNAVAILABLE`, поэтому этап с обязательным фото закрыть было нельзя.

Квитанция архива очков (`photoReceipt`, `archived:true`) подтверждением поручения не является и здесь не используется. Подтверждение - это файл, который сохранил сервер поручений, и строка, которая связывает его с этапом.

## Контракт коротко

| Вопрос | Ответ |
| --- | --- |
| Кто загружает | Только исполнитель этого поручения (`assigneeStaffId`), активный в справочнике, с открытой сменой. Менеджер и хостес не загружают. |
| К какому этапу | К одному этапу своего поручения по `stageCode`. Поручение в работе (`ACCEPTED` или `IN_PROGRESS`), этап ещё не закрыт. Не обязательно текущий этап, как и раньше в правилах. |
| Типы | JPEG, PNG, WebP, HEIC/HEIF. Проверяется содержимое файла (сигнатура), а не имя и не заголовок. |
| Размер | До 10 МБ на файл. До 10 фото на этап. |
| Срок хранения | 30 дней от приёма. После срока файл не отдаётся, запись о нём остаётся в истории поручения. |
| Кто читает | Менеджер и хостес своего заведения. Текущий исполнитель поручения с открытой сменой. Больше никто. |
| Что закрывает фото | Ничего. Фото только засчитывается на этапе. Этап закрывает команда `STAGE_DONE`, поручение - `COMPLETE`. |

## Маршруты

Все маршруты под тем же входом, что и кабинет: JWT отдельного Keycloak Astor, `tenant` и сотрудник берутся из токена. Пока `astor.staff.enabled` выключен, маршруты закрыты совсем.

### Загрузка

`POST /api/staff/tasks/{task}/evidence?eventId=<id>&stageCode=<код этапа>[&capturedAt=<ISO-8601>]`

- Тело запроса - сам файл. `Content-Type` - его тип (`image/jpeg`, `image/png`, `image/webp`, `image/heic`, `image/heif`).
- `eventId` - как у команд: до 64 символов, повтор с тем же `eventId` и тем же файлом возвращает прежний ответ.
- `capturedAt` - когда снято, по часам телефона. Необязательно. Время приёма ставит сервер.
- `tenant`, сотрудник, ключ в хранилище в запросе не передаются и не принимаются.

Ответ `200`:

```json
{
  "evidence": {
    "evidenceId": "5f0c...", "taskId": "a2e1...", "stageCode": "setting",
    "versionAfter": 4, "eventId": "photo-1", "uploadedBy": "<sub сотрудника>",
    "contentType": "image/jpeg", "size": 2381120, "sha256": "<64 hex>",
    "capturedAt": "2026-10-11T08:59:30.250Z", "receivedAt": "2026-10-11T09:00:00.123Z",
    "expiresAt": "2026-11-10T09:00:00.123Z"
  },
  "task": { "...": "поручение с новой версией, счётчик evidence этапа увеличен" }
}
```

Клиент берёт `task.version` из ответа и с ней отправляет `STAGE_DONE`.

| Код | Когда |
| --- | --- |
| `503 EVIDENCE_UNAVAILABLE` | Хранилище не настроено. Как было до этой работы. |
| `403 STAFF_INACTIVE` | Сотрудника нет в справочнике под этой ролью или он выключен. |
| `404 NOT_FOUND` | Поручение чужого заведения или его нет. Существование не раскрывается. |
| `403 FORBIDDEN` | Поручение назначено другому. Менеджер и хостес тоже получают этот отказ. |
| `403 SHIFT_CLOSED` | Смена исполнителя закрыта. |
| `415 UNSUPPORTED_MEDIA_TYPE` | Тип не из списка или содержимое не совпало с заявленным типом. |
| `413 PAYLOAD_TOO_LARGE` | Файл больше лимита. |
| `400 MALFORMED_REQUEST` | Нет `eventId` или `stageCode`, пустое тело, плохой `capturedAt`, неизвестный этап. |
| `409 INVALID_TRANSITION`, `TASK_CLOSED`, `STAGE_CLOSED` | Поручение не в работе, закрыто, этап уже закрыт. |
| `409 EVIDENCE_LIMIT` | На этапе уже 10 фото. |
| `409 EVENT_CONFLICT` | Этот `eventId` уже использован для другого запроса или другого файла. |
| `503 EVIDENCE_STORAGE_UNAVAILABLE` | Хранилище не приняло файл. Ничего не засчитано, можно повторить с тем же `eventId`. |

Порядок проверок: сначала права (сотрудник, заведение, исполнитель, смена), потом читается тело, не дальше лимита. Запрос без прав не доходит ни до чтения файла, ни до хранилища.

### Чтение

| Маршрут | Кто | Ответ |
| --- | --- | --- |
| `GET /api/admin/staff-tasks/{task}/evidence` | менеджер, хостес заведения | `{items: [...]}`, записи как `evidence` выше, до 100 штук, старые первыми |
| `GET /api/admin/staff-tasks/{task}/evidence/{evidenceId}` | менеджер, хостес заведения | байты файла с его `Content-Type` |
| `GET /api/staff/tasks/{task}/evidence` | текущий исполнитель, смена открыта | `{items: [...]}` |
| `GET /api/staff/tasks/{task}/evidence/{evidenceId}` | текущий исполнитель, смена открыта | байты файла |

Файл отдаёт сам сервер: публичных ссылок и подписанных URL нет. Заголовки `Cache-Control: no-store` и `X-Content-Type-Options: nosniff`. Сервер сверяет размер и SHA-256 с записью и не отдаёт файл, если они не совпали.

После переназначения фото остаются при поручении: новый исполнитель их видит, прежний получает `403`. Чужое заведение получает `404`. Фото другого поручения по чужому пути - `404`.

Отказы чтения: `410 EVIDENCE_EXPIRED` (срок вышел или файла в хранилище уже нет), `404 NOT_FOUND`, `403 FORBIDDEN`, `403 SHIFT_CLOSED`, `503 EVIDENCE_STORAGE_UNAVAILABLE`, `503 EVIDENCE_UNAVAILABLE` (хранилище не настроено).

## Что гарантируется при записи

1. Права, повтор события и состояние этапа проверяются чтением, без блокировки заведения.
2. Файл пишется в хранилище. Ошибка хранилища - `503`, на этом всё, в базе ничего не меняется.
3. Одна транзакция под блокировкой заведения, как у всех команд кабинета: права ещё раз, счётчик фото этапа +1, версия поручения +1, запись события, строка аудита `EVIDENCE`, строка `astor_staff_task_evidence`.

Счётчик фото растёт только в шаге 3, а он идёт только после успешного шага 2. Поэтому этап с `evidenceRequired` не закрывается без сохранённого файла.

Если шаг 3 отказал после шага 2 (поручение успели переназначить или отменить), файл остаётся в хранилище без строки в базе. Достать его через API нельзя, удаляет его правило жизненного цикла bucket.

## Связь с версией этапа и аудитом

Своей версии у этапа нет: этап живёт внутри поручения, версия у поручения. Фото привязано к этапу и к версии поручения, которую оно создало.

Таблица `astor_staff_task_evidence` (миграция `2026-10-11-staff-task-evidence`, новая, существующие не менялись):

| Поле | Смысл |
| --- | --- |
| `evidence_id` | идентификатор фото, делает сервер |
| `tenant`, `task_id` | заведение и поручение, `task_id` ссылается на `astor_staff_tasks` |
| `stage_code`, `version_after` | этап и версия поручения после зачёта этого фото |
| `event_id` | событие загрузки. `(tenant, event_id)` ссылается на `astor_staff_task_audit` |
| `uploaded_by` | кто загрузил |
| `content_type`, `size_bytes`, `sha256` | что именно сохранено |
| `object_key` | ключ в хранилище, наружу не отдаётся |
| `captured_at`, `received_at`, `expires_at` | снято, принято, до какого времени отдаётся |

В истории поручения (`GET /api/admin/staff-tasks/{task}/history`) загрузка видна строкой `EVIDENCE` с той же версией, что `versionAfter` у фото.

Чтение фото в аудит не пишется.

## Хранилище

Используется тот же клиент MinIO (`io.minio`), что и в остальном проекте. Bucket отдельный и приватный. Сервис делает только `PutObject` и `GetObject`: не создаёт bucket, не листает, не удаляет, не выдаёт ссылок.

Ключ объекта: `staff-evidence/<SHA-256 от tenant, hex>/<taskId>/<evidenceId>.<расширение>`.

- Префикс заведения: `staff-evidence/<SHA-256 от tenant>/`. Заведение записано хешем, чтобы в ключах не было названий и неудобных символов. Посчитать: `printf %s "<tenant>" | sha256sum`.
- Префикс поручения: внутри префикса заведения, `<taskId>/`.
- Ключ делает сервер. Клиент ключ не выбирает и не видит.

Что нужно от bucket:

- публичного чтения и листинга нет;
- у сервисной учётной записи только `PutObject` и `GetObject` на префикс `staff-evidence/`;
- правило жизненного цикла: удалять объекты под `staff-evidence/` через столько дней, сколько стоит в `retention-days`, и обрывать незавершённые multipart-загрузки.

Срок хранения соблюдается в двух местах: сервер перестаёт отдавать файл после `expires_at`, а сам файл удаляет правило bucket. Сервер файлы не удаляет.

Отказ хранилища клиент видит как `503 EVIDENCE_STORAGE_UNAVAILABLE` без подробностей. В лог сервера попадает только вид отказа (например, `AccessDenied`), без bucket, ключа, адреса и самого файла.

Файл хранится как прислан: не перекодируется, EXIF и геометка не вырезаются. На фото могут попасть гости, поэтому bucket приватный, срок ограничен, ответы не кешируются.

| `astor.staff.evidence.s3-secret-key` | `ASTOR_STAFF_EVIDENCE_S3_SECRET_KEY` | пусто | секрет учётной записи, только в окружении сервера |

| `astor.staff.evidence.content-types` | `ASTOR_STAFF_EVIDENCE_CONTENT_TYPES` | `image/jpeg,image/png,image/webp,image/heic,image/heif` | какие типы принимать, только из этого списка |
| `astor.staff.evidence.retention-days` | `ASTOR_STAFF_EVIDENCE_RETENTION_DAYS` | `30` | срок хранения, от 1 дня |

Отказ в закрытую сторону:

- выключено или не задан любой из четырёх параметров (адрес, bucket, два ключа) - все маршруты фото отвечают `503 EVIDENCE_UNAVAILABLE`, остальной кабинет работает как раньше;
- лимит, срок или список типов заданы неверно - то же самое;
- приложение при этом стартует: в логе одна строка `WARN` с именами свойств, без значений. Неверная настройка фото не должна останавливать монолит, в котором живёт гостевой бот.

## Что понадобится на стенде при включении

Эта работа ничего не включает. Когда дойдёт до включения (вместе с кабинетом, `STAFF_PORTAL_RUNBOOK.md`, раздел 5):

1. Приватный bucket, учётная запись и правило жизненного цикла, как в разделе «Хранилище».
2. Переменные из таблицы в окружении монолита. В `docker-compose.yml` они сейчас не проброшены, как и остальные переменные кабинета (`ASTOR_STAFF_ENABLED` и адреса Keycloak).
3. Шлюз. В `docker/staff/gateway-locations.conf.example` у `/api/staff/` стоит `client_max_body_size 64k` и тайм-аут 15 секунд: фото через такой шлюз не пройдёт. Для одного маршрута загрузки нужен свой лимит чуть выше `max-bytes` и тайм-аут подлиннее. Набросок, на стенде не проверялся, нужен `nginx -t`:

```nginx
location ^~ /api/staff/ {
    # ... как сейчас, 64k ...
    location ~ ^/api/staff/tasks/[^/]+/evidence$ {
        client_max_body_size 11m;
        proxy_pass http://astor_staff_monolith;
        proxy_set_header Authorization $http_authorization;
        proxy_set_header Host $host;
        proxy_read_timeout 60s;
        proxy_send_timeout 60s;
        proxy_cache off;
        access_log off;
    }
}
```

4. Миграция `2026-10-11-staff-task-evidence` применится при старте монолита вместе с остальными, и при выключенном кабинете тоже: одна новая таблица и индекс, существующие таблицы не трогаются. Её нужно включить в репетицию миграций из issue #93.

## Предположения, которые подтверждает Михаил

1. Типы: JPEG, PNG, WebP, HEIC/HEIF. HEIC хранится как есть. Chrome HEIC не показывает, кабинету придётся дать скачать файл или HEIC можно убрать из списка настройкой.
2. Размер: 10 МБ на файл, 10 фото на этап.
3. Срок: 30 дней. Запись о фото (кто, когда, размер, хеш) остаётся после удаления файла.
4. Читают менеджер и хостес своего заведения и текущий исполнитель с открытой сменой. Прежний исполнитель после переназначения не читает.
5. Загружает только исполнитель. Менеджер за него фото не прикладывает.
6. Фото можно приложить к любому незакрытому этапу поручения в работе, не только к текущему. Так уже было в правилах.
7. Формат загрузки: файл в теле запроса, `eventId` и `stageCode` в строке запроса. В черновике P1 был JSON с `imageBase64`. Тело файлом выбрано из-за размера: JSON-команды кабинета ограничены 64 КиБ, а base64 увеличивает фото на треть.
8. Хранилище отдельное от bucket пилота очков и от публичного `astor-media`. Какое именно (Yandex, Cloud.ru или MinIO на VM) решает оператор, код принимает любое S3-совместимое.
9. Заведение в ключе записано хешем, а не названием.

## Чего здесь нет

- iPhone-клиент очков к этому маршруту не подключён. Это отдельное решение по `GLASSES_STAFF_TASKS_P1_DRAFT.md`: у очков сейчас один серверный bearer и нет JWT сотрудника.
- Включение на стенде или в продакшене, bucket, ключи, правка шлюза и `docker-compose.yml`.
- Экран фото в кабинете (`frontend/astor-butler/staff/`).
- Удаление фото по запросу, уменьшенные копии, вырезание EXIF.
- Запись в аудит о том, кто смотрел фото.
- Ограничение частоты загрузок. Тело читается только после проверки прав, но отдельного счётчика запросов нет.

## Проверки

Тесты не требуют bucket: хранилище в них подменено реализацией в памяти за тем же интерфейсом, а адаптер S3 проверен на подменённом клиенте MinIO, как хранилище очков.

- `StaffEvidenceTest` - сценарии от HTTP-маршрута до строк в базе на H2 в режиме PostgreSQL из двух настоящих миграций: этап с обязательным фото закрывается только после сохранённого файла; отказ хранилища ничего не засчитывает; другой исполнитель, менеджер, закрытая смена, чужое заведение получают отказ и в хранилище ничего не попадает; не тот тип, не то содержимое, слишком большой файл; связь с версией и аудитом; повтор и конфликт события; кто читает; срок хранения; выключенное хранилище.
- `PostgresStaffEvidenceTest` - те же сценарии на настоящем PostgreSQL 16. Идёт в CI, локально без `ASTOR_STAFF_TEST_JDBC` пропускается.
- `StaffPortalSecurityTest` - фото проходит мимо лимита JSON только на своём маршруте и только при настроенном хранилище; без токена `401`; при выключенном кабинете маршруты закрыты.
- `S3StaffEvidenceStorageTest`, `StaffEvidenceImagesTest`, `StaffEvidenceUploadTest`, `StaffEvidenceSettingsTest`, `StaffTasksConfigurationTest`, `StaffTaskServiceTest` - ключи и адаптер, сигнатуры файлов, чтение запроса, настройки и отказ в закрытую сторону, правила.
