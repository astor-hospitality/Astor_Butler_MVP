# Astor Glass P1: поручения сотруднику — черновик контракта

Дата: 2026-10-04. Автор: Рома (`0xLaki`). Статус: предложение для ревью Михаила, не реализовано. Собрано из требований в [issue #9](https://github.com/astor-hospitality/Astor_Butler_MVP/issues/9) и [issue #10](https://github.com/astor-hospitality/Astor_Butler_MVP/issues/10). Информационный `/api/glasses/assist` остаётся read-only и этим документом не меняется.

Кликабельный прототип кабинета на учебных данных: `frontend/astor-butler/staff/`. Его данные (`data/staff-demo.json`) повторяют формы из этого документа.

Правила из этого документа реализованы и покрыты тестами как ядро без транспорта и хранилища: ветка `codex/roma-staff-tasks-core`, пакет `api/glasses/tasks`. Контроллера, схемы базы и входа сотрудников там нет, они ждут ответов на открытые вопросы.

## Что должно получиться

Поручение из Concierge или от менеджера попадает конкретному сотруднику на смене, озвучивается в очках, сотрудник отвечает голосом, фото прикрепляется к конкретному шагу конкретного стола, сервер подтверждает статус. Повтор события ничего не дублирует.

## Сущности

| Сущность | Поля | Замечания |
| --- | --- | --- |
| Сотрудник | `staffId`, `tenant`, `displayName`, `role` (`WAITER`, `HOSTESS`, `MANAGER`), `active` | Источник — провайдер идентичности, не клиент |
| Смена | `shiftId`, `staffId`, `tenant`, `startsAt`, `endsAt`, `deviceId`, `status` (`OPEN`, `CLOSED`) | Поручения выдаются только при открытой смене |
| Поручение | `taskId`, `tenant`, `sourceRef`, `tableCode`, `title`, `instruction`, `stages[]`, `priority` (`NORMAL`, `HIGH`), `deadline`, `assigneeStaffId`, `status`, `version` | `tableCode` задаёт сервер, не камера и не фраза сотрудника |
| Шаг | `code`, `title`, `evidenceRequired`, `doneAt` | Порядок шагов фиксирован в поручении |
| Доставка | `deliveredAt`, `voicedAt` | Отдельно от статуса: «доставлено» и «озвучено» не значат «принято» |
| Фото | `evidenceId`, `taskId`, `stageCode`, `capturedAt`, `receivedAt` | Фото получено ≠ шаг или поручение закрыто |
| Событие | `eventId`, `taskId`, `type`, `actor`, `at`, `versionAfter` | История для ленты и разбора |

Статусы поручения: `ASSIGNED` → `ACCEPTED` → `IN_PROGRESS` → `DONE`. Боковые: `HELP_REQUESTED` (возврат в `IN_PROGRESS` после ответа менеджера), `CANCELLED`. Финальные `DONE` и `CANCELLED` не переоткрываются.

## Маршруты сотрудника

Авторизация — токен со scope сотрудника и заведения. `tenant` и `staffId` берутся из токена; значения из тела запроса отвергаются.

| Маршрут | Назначение |
| --- | --- |
| `GET /api/staff/shift/current` | Текущая смена и привязанное устройство |
| `GET /api/staff/tasks?cursor=&limit=` | Только поручения, назначенные вызывающему; `nextCursor` для догона после обрыва связи |
| `POST /api/staff/tasks/{taskId}/delivery` | `{eventId, kind: DELIVERED \| VOICED}` |
| `POST /api/staff/tasks/{taskId}/commands` | `{eventId, type: ACCEPT \| STAGE_DONE \| COMPLETE \| HELP, expectedVersion, stageCode?}` |
| `POST /api/staff/tasks/{taskId}/evidence` | `{eventId, stageCode, imageBase64, imageMimeType, capturedAt}` |

Ответ на команду — поручение с новым `version`. «Принято» и «готово» клиент озвучивает только после этого ответа.

## Маршруты менеджера

| Маршрут | Назначение |
| --- | --- |
| `POST /api/admin/staff-tasks` | Создать и назначить поручение |
| `GET /api/admin/staff-tasks?status=&staffId=&cursor=` | Лента поручений заведения |
| `POST /api/admin/staff-tasks/{taskId}/reassign` | Переназначить, `expectedVersion` обязателен |
| `POST /api/admin/staff-tasks/{taskId}/cancel` | Отменить |
| `GET /api/admin/staff-tasks/{taskId}/evidence/{evidenceId}` | Фото по шагу, по правам заведения |

## Правила

- Идемпотентность: повтор с тем же `eventId` и тем же телом возвращает прежний результат; тот же `eventId` с другим телом — `409`.
- Версии: `expectedVersion` не совпал с текущим — `409` и актуальное поручение в ответе.
- Доступ: поручение чужого заведения отвечает `404`, как несуществующее, чтобы не раскрывать его существование. Чужое назначение внутри своего заведения — `403`. Команды при закрытой смене — `403`.
- Переходы проверяет сервер. Нейросеть распознаёт намерение («стол готов»), но статус не меняет.
- Шаг с `evidenceRequired` не закрывается без фото, шаги закрываются по порядку, `COMPLETE` отклоняется, пока есть незакрытый шаг.
- `ACCEPT` без отметки о доставке допустим и сам считается доставкой: отметка могла потеряться по пути. Отметки доставки не меняют `version`.
- Ошибки в формате пилота: `{requestId, error: {code, message}}`; коды `400`, `401`, `403`, `404`, `409`, `413`, `429`, `503`.
- Фото и голос не логируются. Хранение, срок и удаление фото — по контуру из PR #13.

## Приёмка

1. Два поручения на разные столы у одного сотрудника: фото попадает к своему поручению и шагу.
2. Сотрудник другого заведения получает `404`, другой сотрудник того же заведения — `403`.
3. Повтор команды и фото с тем же `eventId` не создаёт дублей.
4. Команда с устаревшим `expectedVersion` получает `409`.
5. Без смены лента пустая, команды отклоняются.

## Известный пробел

После переназначения лента прежнего исполнителя ничего не сообщает: поручение просто перестаёт в неё попадать. Его команды сервер отклонит, но телефон узнает об этом только при попытке. Нужна отметка «снято» в ленте.

## Открытые вопросы к Михаилу

1. Где живут поручения: в основном монолите с PostgreSQL или в изолированном runtime очков, у которого сейчас нет базы.
2. Вход сотрудников: Keycloak по образцу VEDAL (`backend/keycloak`, `backend/iam`) или отдельный realm для Astor.
3. Кабинет менеджера: отдельное приложение на Next.js как админка VEDAL или раздел текущего сайта.
4. Как запрос Concierge превращается в поручение: автоматически после подтверждения брони хостес или вручную менеджером.
5. Ветка для этой работы: существующая `develop` не обновлялась с июня 2025.
