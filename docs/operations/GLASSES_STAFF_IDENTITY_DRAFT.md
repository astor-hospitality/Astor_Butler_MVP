# Astor Glass P1: вход сотрудников и права — черновик

Дата: 2026-10-04. Автор: Рома (`0xLaki`). Статус: предложение для ревью Михаила. Схема взята из VEDAL Portal (`MuseonUrania`: `backend/keycloak`, `backend/iam`) и приложена к поручениям Astor. Черновик realm'а проверен импортом в локальный Keycloak 26.4.7, результаты в разделе «Что показала проверка импортом». Рабочего Keycloak для Astor нет, проверка подписи токена ни к чему не подключена.

Связанное: контракт поручений `GLASSES_STAFF_TASKS_P1_DRAFT.md` (PR #16), ядро правил в пакете `api/glasses/tasks`.

## Что берём у VEDAL как есть

- Провайдер идентичности покупаем, а не пишем: пароли, блокировки и второй фактор живут в Keycloak. Завести человека, выдать роль и отключить при увольнении — работа консоли Keycloak.
- Клиент интерфейса публичный, с PKCE и без секрета. Сервер токены не выдаёт, только проверяет; для него заведён отдельный клиент `bearerOnly`, имя которого кладётся в `aud`.
- Проверка получателя обязательна. Токен другого клиента того же realm'а подписан теми же ключами, и отличает его только `aud`.
- Роли читаются из `realm_access.roles` и из `resource_access.<клиент>.roles`: стандартный конвертер Spring Security их там не ищет.
- Издатель и адрес ключей настраиваются раздельно: `iss` сверяется с внешним адресом Keycloak, ключи сервер может забирать по внутреннему.
- В файле боевого realm'а нет ни пользователей с паролями, ни секретов.

## Что у Astor по-другому

| Отличие | Почему |
| --- | --- |
| В токене есть заведение: утверждение `tenant` из атрибута пользователя | VEDAL обслуживает одну компанию, Astor рассчитан на много заведений. Заведение берётся из токена, значение из тела запроса не принимается |
| Два публичных клиента: `astor-staff-ui` и `astor-glasses-app` | Кабинет менеджера в браузере и приложение на телефоне официанта входят по-разному, отзывать их нужно независимо |
| Токен живёт 5 минут, у VEDAL 15 | Телефон официанта могут потерять. Отключённая учётная запись перестаёт работать самое позднее через 5 минут |
| Одна учётная запись, одно заведение | Несколько заведений в одном токене потребовали бы выбора заведения в каждом запросе. Токен без заведения или с несколькими отклоняется |

Роли: `astor-waiter`, `astor-hostess`, `astor-manager`. Сейчас хостес и менеджер могут одно и то же; отдельная роль менеджера оставлена под настройки заведения и отчёты.

## Как токен превращается в права

Транспорт проверяет подпись, издателя и срок действия. После этого `StaffScopes` решает, кем этот токен является для поручений:

| Что в токене | Результат |
| --- | --- |
| `aud` не содержит `astor-api` | `401`: токен выписан не для Astor |
| нет `sub` | `401` |
| `tenant` пустой, отсутствует или список | `403`: к учётной записи не привязано заведение |
| нет ни одной роли `astor-*` | `403` |
| всё на месте | заведение из `tenant`, сотрудник из `sub`, самая широкая из ролей |

Роли, выданные для другого клиента, и утверждения неверного вида не дают прав. Это покрыто тестами `StaffScopesTest`.

## Отзыв доступа

Отключить пользователя в Keycloak и завершить его сессии. Уже выданный токен доживает до 5 минут. Смена закрывается отдельно, на стороне поручений: при закрытой смене лента пустая и команды отклоняются сразу, без ожидания.

## Черновик realm'а

`astor-realm.draft.json` лежит рядом. В нём роли, три клиента, отображение `tenant` и объявление атрибута `tenant` в профиле пользователя; пользователей и секретов нет. Адреса возврата указаны только для локального кабинета и условной схемы приложения, боевые нужно вписать при развёртывании.

Значение `tenant` у пользователя должно буква в букву совпадать с кодом заведения в Butler, например `AERIS`: сервер сравнивает строки как есть.

## Что показала проверка импортом

2026-10-04, Keycloak 26.4.7 в Docker на этом компьютере, режим разработки. Четыре временные учётные записи, вход настоящим потоком: код авторизации с PKCE, как это делает браузер. После проверки экземпляр удалён.

**Найденный дефект черновика.** Первая версия импортировалась без ошибок, но заведение у пользователя не сохранялось: Keycloak создаёт пользователя и молча отбрасывает атрибут, которого нет в профиле realm'а. Токены выходили без `tenant`, и сервер отказал бы каждому сотруднику. Исправлено: `tenant` объявлен в профиле, читать и менять его может только администратор. После исправления чистый импорт сразу даёт рабочий realm.

Не чинить это включением произвольных атрибутов (`unmanagedAttributePolicy` = `ENABLED`). Проверено на том же экземпляре: в этом режиме официант через личный кабинет Keycloak записал себе заведение `OTHER`, и следующий токен вышел уже с чужим заведением.

| Проверка | Результат |
| --- | --- |
| Импорт черновика с нуля | Realm, три клиента, три роли на месте; ключи подписи Keycloak создал сам |
| Официант, заведение `AERIS` | `aud` = `astor-api` и `account`, `tenant` = `AERIS`, роль в `realm_access.roles`, срок жизни 300 секунд |
| Менеджер с двумя ролями | Обе роли в токене, сервер берёт более широкую |
| Вход через телефонный клиент | Те же утверждения, `azp` = `astor-glasses-app` |
| Учётная запись без заведения | Токен без `tenant`, сервер отвечает `403` |
| Учётная запись без роли Astor | Сервер отвечает `403` |
| Тот же человек, вход через личный кабинет Keycloak | `aud` = `account`, без `astor-api`: сервер отвечает `401` |
| Сотрудник меняет себе `tenant` через личный кабинет | `400`, атрибут только для чтения; в новом токене прежнее заведение |
| Код заведения с пробелом | Keycloak отклоняет при сохранении |
| Вход без PKCE | Отказ: `Missing parameter: code_challenge_method` |
| Обмен кода с чужим `code_verifier` | Отказ: `PKCE verification failed` |
| Чужой адрес возврата | Отказ: неверный `redirect_uri` |
| Пароль напрямую в адрес выдачи токенов | Отказ: клиенту это запрещено |
| Серверный клиент `astor-api` просит токен | Отказ |

Утверждения из выданных токенов сохранены как тестовые данные (`src/test/resources/glasses/keycloak-26-token-claims.json`, без самих токенов и паролей), и `StaffScopesTest` проверяет ими разбор прав.

Что проверка не покрывает: подпись и срок токена сервер пока не проверяет вовсе; в черновике `sslRequired` = `all`, поэтому по обычному `http` realm не отвечает, и для проверки это требование было снято только в локальном экземпляре; вход с настоящего телефона по схеме `astorglass://` не проверялся.

Замечание по составу токена: стандартные настройки Keycloak добавляют в него получателя `account` и роли личного кабинета. Сотрудник может открыть личный кабинет и поменять себе имя и почту. Заведение и роли поменять не может.

## Чего не хватает до работающего входа

1. Запущенного Keycloak для Astor с этим realm'ом. Локально импорт проверен, боевого экземпляра нет.
2. Проверки подписи токена в сервере. В VEDAL это `KeycloakDecoderConfig`; изолированный runtime очков сейчас без Spring Security и проверяет один статический токен.
3. Привязки очков и телефона к сотруднику. Сейчас сотрудник определяется только учётной записью.
4. Справочника сотрудников и смен для кабинета. В VEDAL список берётся из административного API Keycloak служебной учётной записью с одним правом на чтение.

## Вопросы к Михаилу

1. Отдельный realm `astor` в том же Keycloak, что у VEDAL, или отдельный Keycloak. Общий экземпляр проще в сопровождении, но связывает два проекта общим обновлением и общей точкой отказа.
2. Где проверять токен: добавить Spring Security в runtime очков или держать поручения в основном монолите, где он уже есть.
3. Как открывается и закрывается смена: кнопкой в приложении официанта, менеджером в кабинете или по расписанию.
