# Concierge → Butler → Saby: передача брони стола — черновик

Дата: 2026-10-04. Автор: Рома (`0xLaki`). Для Димы (сторона Saby), для стороны Concierge и для ревью Михаила.

Документ описывает, что уже есть в коде Butler, и что нужно доделать, чтобы внешний Concierge мог оформить бронь, а Saby получил её как внешняя система ресторана. Описание взято из кода (`api/booking/BookingController`, `domain/booking/TableReservationService`, `domain/booking/TableReservationRepository`, `integration/saby/*`) и проверено вживую 2026-10-04: Butler поднят локально на чистой базе, запросы из раздела 1 выполнены, ответы ниже настоящие. Telegram при проверке был выключен, поэтому карточка хостес не отправлялась, а решение принималось запросом `confirm`. Чистая база потребовала исправления миграций, см. раздел 5.

Адрес в примерах — локальный gateway `http://localhost:8080`. Время передаётся в UTC: 14:00 в Екатеринбурге это `09:00Z`.

## 1. Что работает уже сейчас

Цепочка та же, что на слайде «Роли Concierge, Butler и Aeris»: заявка → карточка хостес → подтверждение человеком.

### Шаг 1. Свободные столы

```bash
curl "http://localhost:8080/api/bookings/tables/availability?venueCode=AERIS&from=2026-10-07T09:00:00Z&to=2026-10-07T11:00:00Z&partySize=2"
```

Ответ `200`: список свободных столов, на чистой базе их 20. Ответы в примерах настоящие, часть полей опущена.

```json
[
  {
    "table": { "id": 4, "venueCode": "AERIS", "tableCode": "4", "displayName": "Стол 4 · у окна", "zone": "WINDOW", "capacityMin": 1, "capacityMax": 5, "bookable": true, "active": true },
    "available": true,
    "reason": "AVAILABLE"
  }
]
```

### Шаг 2. Заявка на бронь

```bash
curl -X POST http://localhost:8080/api/bookings/table-reservations -H "Content-Type: application/json" -d '{"chatId":123456,"venueCode":"AERIS","requestedStartAt":"2026-10-07T09:00:00Z","requestedEndAt":"2026-10-07T11:00:00Z","partySize":2,"guestName":"Michael","guestPhone":"+79990000000","guestComment":"Бизнес-ланч, заявка от Concierge"}'
```

| Поле | Обязательно | Замечание |
| --- | --- | --- |
| `chatId` | да | Сейчас это чат гостя с ботом в Telegram |
| `requestedStartAt`, `requestedEndAt` | да | Конец позже начала |
| `partySize` | да | Не меньше 1 |
| `venueCode` | нет | Без него берётся `AERIS`: заявка без заведения создалась на стол AERIS |
| `tableCode` | нет | Если не указан, берётся первый свободный стол, сначала в `preferredZone` |
| `preferredZone`, `seatingPreference`, `guestName`, `guestPhone`, `guestComment` | нет | Попадают в карточку хостес |

Ответ `201`: заявка в статусе `AWAITING_MANAGER_CONFIRMATION`, стол удержан. В чат команды уходит карточка с кнопками «Да» и «Нет».

```json
{
  "id": 1,
  "chatId": 123456,
  "tableId": 4,
  "tableCode": "4",
  "tableDisplayName": "Стол 4 · у окна",
  "status": "AWAITING_MANAGER_CONFIRMATION",
  "requestedStartAt": "2026-10-07T09:00:00Z",
  "requestedEndAt": "2026-10-07T11:00:00Z",
  "partySize": 2,
  "guestName": "Michael",
  "guestPhone": "+79990000000",
  "managerTelegramId": 876857557,
  "hostessChatId": null,
  "sbisExternalId": null
}
```

### Шаг 3. Решение

```bash
curl http://localhost:8080/api/bookings/table-reservations/1
```

Статус меняется на `CONFIRMED` или `REJECTED`. Решение принимает хостес кнопкой в Telegram; то же делают `POST /api/bookings/table-reservations/{id}/confirm` и `/reject`. Кнопки работают только из чата, записанного в `TELEGRAM_HOSTESS_CHAT_ID`.

### Ошибки

Формат один: `{code, message, traceId, details, timestamp}`.

| Код | Когда |
| --- | --- |
| `400 BAD_REQUEST` | Нет `chatId`, времени или числа гостей; конец не позже начала |
| `404 NOT_FOUND` | Указанный стол или заявка не найдены |
| `409 CONFLICT` | Стол занят на это время, не вмещает гостей, не бронируется; свободных столов нет; заявка уже не ждёт решения |

Не использовать `POST /api/bookings` без `table-reservations`: это заглушка, она возвращает случайный номер и ничего не сохраняет.

## 2. Чего не хватает для Concierge

| Пробел | Что происходит сейчас | Что нужно |
| --- | --- | --- |
| Ответ гостю | Подтверждение и отказ уходят сообщением в Telegram по `chatId`. Гость, пришедший через Concierge, мог не запускать бота Butler | Канал ответа для внешнего источника: обратный вызов Concierge или его опрос |
| Источник заявки | При вставке жёстко пишется `source = 'TELEGRAM'`. Проверено: все три тестовые заявки, созданные через API, записаны как `TELEGRAM` | Поле источника в запросе и в ответе |
| Повторы | Повтор запроса без `tableCode` удерживает второй стол. Проверено: первая заявка получила стол 4, точно такая же вторая — стол 5 | Ключ идемпотентности от Concierge |
| Согласие гостя | В Telegram гость сначала отдаёт контакт и согласие. Заявка через API эту проверку обходит | Ссылка на согласие, полученное на стороне Concierge |
| Срок удержания | В удержание записывается срок: начало брони плюс 15 минут, но его никто не читает. Проверено: срок переведён в прошлое, стол остался занят, новая заявка на него получила `409`, прежняя осталась в ожидании. Если хостес не ответит, стол на это время занят бессрочно | Истечение удержания и статус `EXPIRED` |
| Доступ | `SecurityConfig` разрешает всё. Подтвердить чужую бронь может любой, кто дотянется до адреса | Авторизация до того, как API станет доступен снаружи |
| Уведомление Concierge | Нет | Обратный вызов или событие о смене статуса |

Для показа связки эти пробелы не мешают: заявка создаётся, хостес подтверждает, статус читается. Для настоящих гостей мешают все.

## 3. Граница с Saby

Сейчас Saby в бронировании не участвует.

- Интерфейс `ExternalReservationProvider` описывает четыре действия: `providerId`, `status`, `checkAvailability(запрос)`, `reserve(команда, ключ идемпотентности)`.
- `SabyReservationProvider` — заглушка. Без настроек отвечает «не настроено», с настройками — «не реализовано».
- `TableReservationService` этот интерфейс не вызывает. Свободные столы и удержания считаются по собственной базе Butler.
- Поле `sbisExternalId` в заявке и в ответе есть, но его никто не заполняет.

Настройки, которые адаптер ждёт (значения только в серверном окружении, не в git):

```text
ASTOR_SABY_ENABLED
SABY_API_BASE_URL
SABY_AUTH_METHOD
SABY_ORGANIZATION_ID
SABY_RESTAURANT_ID
SABY_AVAILABILITY_PATH
SABY_RESERVATION_PATH
SABY_API_TOKEN или SABY_CLIENT_ID + SABY_CLIENT_SECRET + SABY_REFRESH_TOKEN
```

### Что нужно от Димы

1. Подтверждение, что у Saby Presto есть программный доступ именно к бронированию столов, и ссылка на документацию. В черновиках договора это отмечено как неподтверждённое.
2. Тестовый доступ: адрес, способ авторизации, идентификаторы организации и ресторана.
3. Два вызова на стороне Saby: проверить доступность на время и число гостей; создать бронь с нашим номером заявки как ключом идемпотентности.
4. Что Saby возвращает: свой номер брони, статус, подтверждённый стол и время, причину отказа.
5. Ограничения: частота запросов, тариф, какие данные гостя разрешено передавать.

### Что Butler передаёт в Saby

После согласия гостя: номер заявки Butler (он же ключ идемпотентности), заведение, стол или зону, время начала и конца, число гостей, имя и контакт, если гость их дал, комментарий, источник заявки.

### Что при сбое Saby

Заявка в Butler сохраняется, хостес получает карточку как сейчас, гостю не обещается подтверждённая бронь. Saby не обходит подтверждение человеком, пока это отдельно не согласовано.

## 5. Что показала проверка вживую

Локальный запуск: PostgreSQL, Redis, MongoDB и Kafka в Docker, приложение из исходников, Telegram и внешние модели выключены.

| Проверка | Результат |
| --- | --- |
| Свободные столы на 07.10, 14:00–16:00 по Екатеринбургу, 2 гостя | `200`, 20 столов |
| Заявка без указания стола | `201`, стол 4, `AWAITING_MANAGER_CONFIRMATION` |
| Та же заявка повторно | `201`, стол 5: вторая бронь вместо отказа |
| Заявка на уже удержанный стол 4 | `409`, `Table already has an active hold for this time window` |

| `reject` | `200`, `REJECTED`, удержание снято |
| Удержание с истёкшим сроком | Стол остаётся занят, новая заявка на него получает `409`, прежняя заявка не меняет статус |
| Без `chatId` | `400`, `chatId is required` |
| Несуществующий стол | `404`, `Requested table was not found` |
| Несуществующая заявка | `404`, `Table reservation was not found` |
| `POST /api/bookings` | `201` со случайным номером и статусом `DRAFT`, в базу ничего не пишется |
| Диалог брони гостя, сценарий `scripts/replay_scenarios/table-booking-happy-path.jsonl` через `POST /api/messages` | 7 шагов из 7: согласие, контакт, 3 гостя, «подбери сам», завтра, 19:00. Создана заявка на стол 4 в статусе `AWAITING_MANAGER_CONFIRMATION` |

Диалог и запросы из раздела 1 пишут в одну таблицу заявок и одно удержание столов. Проверено: после диалога запрос через API на тот же стол 4 с пересекающимся временем вернул `409`, а в списке свободных столов на это время осталось 19 из 20. Заявка от Concierge и заявка из Telegram один стол на одно время не займут. Скрипт `scripts/replay_fsm_scenario.sh` требует `jq`; на машине без него те же запросы и проверки выполнялись отдельно.

**Миграции базы.** На чистой базе приложение стартовало, отвечало `UP` на проверку состояния и не имело ни одной таблицы: все запросы к базе возвращали `500`. После перехода на Spring Boot 4 в проекте остался только `liquibase-core`, а автозапуск миграций в этой версии вынесен в отдельный модуль. Исправление и тест лежат в ветке `codex/roma-liquibase-boot4-fix`. До него на чистой базе этот документ не воспроизводится. Перед выкладкой исправления нужно проверить таблицу `databasechangelog` на боевой базе: после выкладки приложение начнёт сверять и применять миграции при старте.

**Образы хранилища файлов.** `minio/minio` и `minio/mc` с тегами из `docker-compose.yml` больше не скачиваются с Docker Hub. Для брони хранилище не нужно, но полный стек по текущему compose-файлу на новой машине не поднимется.

## 6. Бизнес-ланч: Concierge → сценарий Butler → Saby

Добавлено 2026-10-06 по поручению Михаила. В отличие от раздела 1, заявка идёт не прямым запросом в API, а через FSM, как остальные сценарии гостя: согласие, шаги, сводка, подтверждение гостем.

### Как Concierge передаёт гостя

Два входа, смысл один.

1. Ссылка в бот заведения. В ленте это кнопка «Бизнес-ланч» (поле `lunchUrl` в `data/venues.json`).

```text
https://t.me/astor_butler_bot?start=lunch_aeris
https://t.me/astor_butler_bot?start=lunch_aeris_s2_p2_d20261007_t1300_r7f3a
```

Бот получает текст `/start lunch_...`. Первым идёт код заведения, дальше в любом порядке и по желанию: `s` номер комбо из файла меню, `p` число гостей, `d` день `ГГГГММДД`, `t` время `ЧЧММ`, `r` номер запроса Concierge. Telegram допускает в параметре до 64 символов из набора `A-Z a-z 0-9 _ -`.

2. Сообщение в шлюз `POST /api/messages` с тем же содержанием в `payload`:

```json
{"channel": "TELEGRAM", "chatId": 123456, "text": "Бизнес-ланч", "payload": {"concierge": {"scenario": "BUSINESS_LUNCH", "venueCode": "AERIS", "setCode": "STARTER_MAIN", "partySize": 2, "date": "2026-10-07", "time": "13:00", "requestId": "c-118"}}}
```

Обязателен только признак сценария. Что не передано или передано неверно (несуществующее комбо, суббота, 19:00, сорок гостей), бот спросит сам. Гость может начать и без Concierge, написав боту «бизнес-ланч».

### Что делает Butler

| Состояние FSM | Вопрос гостю |
| --- | --- |
| `BUSINESS_LUNCH_CHOOSE_SET` | Какое комбо |
| `BUSINESS_LUNCH_CHOOSE_DISH` | Блюдо для каждой позиции комбо, где есть выбор |
| `BUSINESS_LUNCH_COLLECT_PARTY_SIZE` | Сколько гостей |
| `BUSINESS_LUNCH_COLLECT_DATE` | День, только дни ланча |
| `BUSINESS_LUNCH_COLLECT_TIME` | Время, только часы ланча |
| `BUSINESS_LUNCH_CONFIRMATION` | Сводка и «Отправляю заявку команде?» |

- Новый гость по ссылке сначала проходит согласие и контакт. Переданное из Concierge ждёт и после контакта диалог продолжается с ланча.
- Без «да» гостя на сводке ничего не создаётся.
- После «да» создаётся обычная заявка на стол (удержание, карточка хостес, подтверждение человеком) с пометкой «Бизнес-ланч» и составом заказа в комментарии. Гостю бронь подтверждённой не называется.
- Повтор той же заявки тем же гостем на то же время второй стол не удерживает.
- Выйти можно на любом шаге: «отмена» или кнопка «Отменить».

Меню ланча лежит в `src/main/resources/business-lunch/<заведение>.json`: дни, часы, блюда по курсам, комбо с ценой. Для AERIS сейчас стоят «Салат дня», «Суп дня», «Горячее дня» без цен и окно «будни 12:00–16:00»; поле `confirmedByVenue` равно `false`, и бот говорит гостю, что состав и стоимость подтвердит команда. Настоящее меню подставляется заменой файла.

### Что уходит в Saby

Результат диалога передаётся в порт `ExternalLunchOrderProvider.submit(order, idempotencyKey)`. Ключ идемпотентности: `astor-lunch-<номер заявки Butler>`.

| Поле заказа | Содержание |
| --- | --- |
| `venueCode`, `tableReservationId`, `tableCode` | Заведение, номер заявки Butler, удержанный стол |
| `startAt`, `endAt`, `guests` | Время в UTC и число гостей |
| `setCode`, `setTitle`, `setPriceRub` | Комбо |
| `dishes[]`: `courseCode`, `dishCode`, `dishTitle` | Выбранные блюда |
| `guestName`, `guestPhone`, `comment` | Гость и его пожелание |
| `source`, `conciergeRequestId` | `CONCIERGE` или `DIRECT`, номер запроса Concierge |

`SabyLunchOrderProvider` пока заглушка, как и `SabyReservationProvider`: выключен по умолчанию, без настроек отвечает `PROVIDER_NOT_CONFIGURED`, с настройками `PROVIDER_CONTRACT_NOT_IMPLEMENTED`, наружу ничего не вызывает. Диме остаётся сопоставить коды комбо и блюд с номенклатурой Saby и реализовать вызов.

- Saby выключен: в комментарии для хостес стоит «В Saby внести вручную».
- Saby включён и принял заказ: его номер записывается в заявку (`sbisExternalId`).
- Saby включён и не принял: заявка остаётся, администратор получает сообщение «внесите вручную».

В любом случае итог гостю сообщает хостес, а не Saby.

### Чего здесь нет

- Разных блюд для разных гостей за одним столом: одно комбо на всех, остальное гость пишет пожеланием.
- Оплаты и предоплаты.
- Повторной отправки в Saby после сбоя: только сообщение администратору.
- Проверки вместимости под ланч отдельно от обычных столов.
