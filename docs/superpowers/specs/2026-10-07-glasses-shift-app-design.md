# Astor Glass: рабочее приложение смены и журнал с отчётом

Дата: 2026-10-07. Автор: Claude по заданию Михаила (issue #46). Согласовано в чате 07.10 09:10 Екб: показа не делаем, делаем рабочее приложение для персонала; реальные поручения (P1) — отдельной веткой позже.

## Цель

Сотрудник надевает очки и работает смену: спрашивает голосом, снимает фото, получает ответ в наушник, принимает звонки, ставит очки на зарядку и материалы уходят в архив. Мы после смены открываем одну страницу и видим, что он спрашивал, что Астор ответил, где была ошибка и сколько это заняло.

Границы не меняются: Astor Glass информационный. Ни ACK, ни поручений, ни броней, ни FSM-переходов. Один серверный bearer, приватный S3, изолированный runtime.

Остаётся: подключение/переподключение, вопрос голосом, фото «что я вижу», чек-лист подачи на двоих (4 шага, рабочие формулировки), приветствие при надевании, звонки, выгрузка архива при зарядке кейса, журнал смены.

## 2. Backend (изолированный glasses API)

### 2.1 Контекст сессии для любого запроса

`photoContext` принимается и для текста, и для аудио (имя на проводе не меняем ради совместимости). Для не-фото запросов `photoReceipt` не выдаётся. Сценарии: `BUSINESS_LUNCH_TWO` (4 шага подачи) и `SHIFT` с единственным шагом `SHIFT_ASSIST` — чтобы вопросы вне чек-листа тоже попадали в журнал смены.

### 2.2 `POST /api/glasses/session-events`

Тот же bearer, общий лимит 10/мин. Тело: `{requestId, sessionId, scenarioCode, events:[{at, type, stageCode?, note?}]}`, 1–50 событий, типы `STEP_STARTED|STEP_DONE|CALL_STARTED|CALL_ENDED|SESSION_FINISHED|CLIENT_ERROR`, `note` ≤ 200 символов, `at` в пределах ±24 ч. Идемпотентно по `requestId`; другое тело под тем же id — 409. Ничего не подтверждает.

### 2.3 `GlassesSessionJournal`

В памяти: ≤ 32 сессий на scope, TTL 24 ч, ≤ 500 записей. Запись `assist`: время, вид (text/audio/image), шаг, requestId, ответ или код ошибки, задержка, `archived`. Переполненная сессия тихо перестаёт писать записи — журнал никогда не ломает ответ сотруднику. Каждые 2 с изменённые сессии пишутся в S3: `materials/<scope>/sessions/<id>/journal.json`; неудачная запись остаётся «грязной» и повторяется. Сырых медиа и транскриптов в журнале нет.

### 2.4 Отчёт

- `GET /api/glasses/sessions` — список сессий scope со сводкой.
- `GET /api/glasses/sessions/{id}/report` — HTML без скриптов: шаги с длительностями, звонки, таймлайн с ответами, задержками и ошибками, фото через `…/photo/{requestId}`.
- `GET /api/glasses/sessions/{id}/photo/{requestId}` — стримит `input.jpg` из S3 только для запроса, который есть в журнале как фото; отказ архива — 404, на странице «фото недоступно».

Доступ — HTTP Basic, пользователь `astor`, пароль из `ASTOR_GLASSES_REPORT_PASSWORD` (≥ 12 символов), 30 запросов в минуту, `Cache-Control: no-store`, CSP `default-src 'none'`. Это не мобильный bearer; мобильный клиент отчёт не открывает.

## 3. Проверки

JUnit: контекст для текста/аудио и журналирование ответа и ошибки; валидация, идемпотентность и лимиты session-events; журнал (порядок, вытеснение, TTL, переполнение, запись и чтение S3); рендер отчёта (экранирование, шаги, звонки), Basic-auth (401/503), фото 404 при отказе архива. clang: чек-лист подачи, очередь событий, реакция на звонок. Java локально не компилируется из облачной среды — CI обязателен.
